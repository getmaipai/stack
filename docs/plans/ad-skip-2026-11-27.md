# Ad skipping for podcasts and other media (plan, 2026-11-27)

Status: plan only, nothing built. Asked by Jesse 2026-11-27: review MinusPod, decide
run-it-or-port-it, decide Home or Stack, look at other approaches, cover media beyond podcasts.

## Bottom line

1. **Port the ideas, do not run MinusPod.** It is MIT, so copying is allowed with its notice,
   but it is a second app (Python 3.12, Flask, SQLite, Docker, about 137k lines of Python and
   104k of TypeScript) that duplicates what Stack and Home already own: transcription, an LLM
   role, a job queue, feeds, accounts and a UI.
2. **A Stack service, Home only has the screens (Jesse, 2026-11-27).** The Stack gets a `segments`
   service: it fetches the audio (probing for a clean copy), transcribes, detects, keeps the
   result by file hash in its own database and serves the segment list and a cut copy. It never
   knows who is asking. Home keeps subscriptions, per-person and per-show settings and all UI.
3. **Work on the hub's own copy of the audio, and skip on that copy.** Services insert dynamic
   ads (see the next section), so timestamps from one stream do not fit another. The hub
   fetches each episode once, keeps that file, detects on it, and the player plays that file
   with a list of ranges to jump over (a cut copy is rendered for export). Streaming the
   publisher's URL directly cannot be skipped reliably; it stays as the no-skip fallback.
4. **One record for all media:** `media-segments` (spec, in `commons`, first): `kind`
   (`ad`, `sponsor`, `selfpromo`, `intro`, `outro`, `recap`, `filler`), `start`, `end`,
   `confidence`, `source` (`fingerprint`, `text-pattern`, `llm`, `person`, `chapter`),
   `status` (`auto`, `held`, `confirmed`, `rejected`), and the revision of the transcript and
   model that produced it.

## What MinusPod does (v2.102.23, reviewed by reading, not run)

Pipeline, in order: transcribe (faster-whisper, Parakeet or a remote Whisper); match known ads
before any LLM (Chromaprint fingerprints, TF-IDF and fuzzy text patterns, jingle templates,
cross-fetch and publisher-transcript differentials); LLM detection over 10-minute windows with
3 minutes overlap; a validator (confidence 0.80 and up is cut, 0.50 to 0.79 is held for review,
below that is dropped; duration, position and sponsor-name checks); boundary snapping to
silence and cue sounds; ffmpeg cut with MP3 stream copy where possible; a verification pass that
re-transcribes the result and asks what does not belong; chapters; a rewritten RSS feed. Your
corrections become patterns. UI: feeds, episode waveform editor, review queue, patterns,
sponsors, LLM cost, settings. A local OpenAI-compatible LLM works (`OPENAI_BASE_URL`).
Its YouTube support only turns a channel into an audio feed, using SponsorBlock marks and
captions; it does not edit video.

Worth taking: the window and overlap scheme, the validator thresholds and held-for-review
state, silence and cue boundary snapping, the verification re-listen, fingerprint-first
matching, the correction-to-pattern loop. Not worth taking: the feed server, the UI, the
database, the provider router, notifications, backups, accounts.

## Dynamic ad insertion (Jesse, 2026-11-27)

Services change the ads and the insertion points on every stream, so a "skip at 12:40" list
made from one stream is wrong on the next. What follows from that:

- Segments belong to one stored copy, never to the episode in general. The record carries the
  file hash it was made for. A new fetch is a new file and is analysed again.
- The hub is one listener, so it fetches once and every person plays that copy. Ads are then
  fixed in that file and detection only has to be right once per episode.
- Two fetches expose the inserted spans: same episode fetched twice (ideally with different
  listener identity) differs exactly where ads were stitched in. MinusPod calls this the
  cross-fetch differential. Cheap, needs no model, strongest signal for inserted ads.
- Fingerprints get more useful, not less: the same ad creative repeats across fetches and
  episodes even when its position moves. Match by content, never by time.
- Boundary refinement matters: stitched ads join the show audio with a loudness or encoder
  seam, which silence and splice detection can find.
- Limits: a service that serves ads only to its own app, or signs per-listener URLs, may give
  the hub nothing but the ad-free or the fallback audio (likely what our plain downloads
  returned). Phase 0 must test the real feeds Jesse listens to, fetched the way the hub
  fetches them.
- We never fake a listening app's identity to get ads; we process what the hub is served.
  (Open question for Jesse: MinusPod does vary the User-Agent per feed. See the next section.)

### What others actually see (research, read from MinusPod's issues and docs, 2026-11-27)

- Verified: the User-Agent decides whether a download is ad-free or stitched. MinusPod issue
  #836 measured one episode from one IP: one host gave +115 s with a Chrome string, the original
  length with curl, +120 s with an iTunes string; another publisher on the same host gave +400 s
  for Chrome and curl but the original length for the iTunes string. No single UA works for all
  feeds. MinusPod added a per-feed download-UA override and keeps separate UAs for RSS and audio.
  So our plain downloads returning clean audio is the normal outcome, not a bug.
- Verified: insertion rotates per request, not per IP (issue #359). Two fetches can return the same
  ad or a different count of breaks, so a two-fetch diff alone is unreliable; MinusPod never cuts
  on the diff alone, only when fingerprint, transcript or audio-cue evidence overlaps, and holds
  the rest for review. Some CDNs re-encode on the second download and make good audio look
  different (issue #541, fixed by discarding whole-file mismatches).
- Verified: publisher transcripts (`podcast:transcript`) are often made before ads are inserted, so
  the transcript-differential works only on some shows and never auto-cuts (held for review).
- Practical probe, cheap and honest: compare downloaded length with the feed's stated
  `itunes:duration`. Equal means a clean copy (use it as the reference), longer means stitched.
- Not found anywhere: a documented way to get the exact audio Apple's app receives, which hosts
  serve clean audio to unknown clients, or any Podly report on this. Treat those as unknown.
- Consequence for Jesse's idea (match a clean copy against the stitched stream): sound and
  consistent with this. A clean reference exists when the probe says so; align by audio
  fingerprint and treat unmatched stretches as inserted, edges refined by silence and seams.
  When no clean copy can be had, fall back to content detection (fingerprint library, LLM).

## Other approaches (short)

- **Podly** (MIT, active): same design as MinusPod. Confirms the shape, adds nothing.
- **Cross-episode fingerprint matching** (Adblock Radio, a Google patent): the same ad read
  or dynamically inserted spot repeats across episodes of a show, so match audio fingerprints
  against earlier episodes and known ads. Local, cheap, handles inserted ads that the LLM
  sees as normal speech. MinusPod already does the Chromaprint part.
- **Small sentence classifiers** (Spotify's BERT ad model, a DistilBERT one on Hugging Face):
  fast first pass so the big model reads only suspect windows. Useful for cost on a small box.
- **Audio plus text features** beat either alone in a 2025 thesis; supports using silence,
  loudness and music-bed cues next to the transcript.
- **SponsorBlock** (video): crowdsourced segments keyed by YouTube id; the data is CC BY-NC-SA
  4.0, so a public MaiPai release cannot ship it. Fine as optional lookup or as evaluation
  labels on the owner's machine; legal check first.
- **Comskip and Jellyfin media segments** (TV recordings): black frames, silence and logo
  detection write EDL or segment files. Only relevant if the Shows app records live TV.

Nothing found beats "fingerprint first, small classifier second, local LLM third, human
correction last" for a private home box.

The file the feed serves to a plain download carries no inserted ads, and the hosts read none.
The Apple link Jesse gave names "Wish Upon LIVE! (Classic)", a different episode from Hello
Mary Lou; it was not transcribed (a script error skipped it; rerun pending). Ads on this show
are probably inserted per listener by the ad network, so a plain download may never see them.
**To prove real ad removal we need an ad-bearing episode: a show with host-read sponsors
(most comedy and news shows) or a copy of the audio exactly as a listening app receives it.**

What did run: on Christmas Cupid the transcript clearly marks two self-promo blocks (a
producer's listener-message request at 3942 to 3987 s, a cross-promo for two other shows at
4040 to 4076 s). Cutting both with ffmpeg gave a 68:23 file from 69:44 (81 s removed). That
shows the cut stage, not detection quality.

Takeaways: the clean-copy alignment method gives exact edges with no model; it needs a clean
reference, which only some hosts give. Where ads are baked in, transcript detection is the only
route, and the lead-in phrases and sponsor-read text were easy to spot. Boundaries were chosen
by me from the transcript in this demo; the product must do this with the local LLM and the
validator, then be measured against hand labels (Phase 0).

## Plan

Phase 0 (S, one session): fetch each test episode twice and diff, then get an ad-bearing episode and the first honest measurement.
Pick three shows with host-read sponsors, label ads by hand on one, run the pipeline, report
precision, recall and boundary error in seconds. Decides whether the LLM needs a larger
model. No product code.

Phase 1 (M): the record and the Stack job. Spec `media-segments` in `commons` (spec first).
Stack: job kind `segments` using the `stt` long-file job, the `chat` role for windows,
Chromaprint for fingerprints, the validator and boundary snapping ported from MinusPod with
tests on recorded transcripts. Admin page row and `integrations.md` entry. Offline tests with
scripted engines per the Stack's rules. Privacy: no new outbound endpoint.

Phase 2 (M): Home Podcasts. Setting per show (skip, mute with a tone, mark chapters, off),
auto-skip in the player from the record, a "skipped 2 breaks" pill with undo, held-for-review
list for 0.50 to 0.79, a segment editor on the episode page, corrections saved as patterns
scoped to the show. Cut copy rendered on Save. Children: on by default, no review UI.

Phase 3 (M): learning. Cross-episode fingerprint library per show, repeated-ad detection,
small classifier prefilter if cost needs it, benchmark set kept in `data-scratch`.

Phase 4 (S each): other media through the same record. Videos: captions or `stt` plus the
same LLM, kinds `sponsor`, `selfpromo`, `intro`, `recap`; the player skips like podcasts.
Shows and Films: intro and recap skip first; commercial detection (Comskip style) only if
live TV recording exists. Music and radio: none, there is nothing safe to skip.
Audiobooks: none.
