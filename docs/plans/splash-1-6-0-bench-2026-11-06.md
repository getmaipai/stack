# Splash 1.4.1 to 1.6.0 on the Studio (2026-11-06)

Pins moved: `splash-chat` and `splash` (coding) from 1.4.1 to 1.6.0. Archive `splash-1.6.0-arm64-macos26.tar.gz`, sha256
`da3aef0a581491b0eb4c1168bda07f520e5ca8368764abff426d95ac1c77e5c4`, 79,846,781 bytes (GitHub release asset digest, the release's `SHA256SUMS`
and the downloaded file all agree). Release notes: `https://github.com/incoai/splash/blob/1.6.0/docs/release-notes/1.6.0.md`. The Stack skipped 1.5.0.

## What 1.6.0 changes that the Stack touches

| Change in 1.6.0 | Effect on the Stack |
|---|---|
| `/status` schema 8 (`memory_governor` ledger; two fields removed) | None. The Stack does not read `/status` fields. |
| Stop sequences: a single string is a 400; each item needs a non-whitespace character; over 16,384 characters is a 400 | Real. Measured: 1.6.0 answers 400 `stop_sequences must be an array of strings` to a string on `/v1/messages`; 1.4.1 took it. The coding Messages wire now normalizes a string to an array (`normalizeStopSequences`). The OpenAI chat `stop` field is unchanged. The 16,384 limit is not enforced by the Stack; the engine's 400 reaches the caller. |
| GGUF screening (tensors the model would not apply are refused) | Both pinned GGUFs load: Qwen3.8-27B UD-Q4_K_M (coding, language only) and Huihui UD-IQ4_XS (chat). No refusal. |
| `--expert-memory auto`, SSD cache shrink, `--max-memory` ledger | Launch flags in `engineArgs.ts` unchanged and accepted (`--max-context`, `--max-memory`, `--max-cache-disk 0`, `--idle-release off`, `--served-model-name`, `--announce-served-name`, `--thinking-token-budget`, `--language-only`, `--no-webui`, `--offline`). |
| Restart backoff, 400 `request_quarantined`, 503 `engine_recovering` with `Retry-After` | A killed engine returned 503 until it served again, then 200. No `request_quarantined` seen. |
| PDF input needs `/usr/bin/sandbox-exec` | Stack sends no PDFs to Splash. Not exercised. |
| `POST /v1/chat/completions/count_tokens` | Works (HTTP 200). The Stack does not call it. |
| Model cache rebuilt once after upgrade | Seen once: the first start of the new binary took 252 s to become ready (and the first restart after it 249 s); every later start 13 to 43 s. |

## Method

the bench driver (kept in Home's git-ignored `data-scratch/splash160/run.sh`): the launcher exactly as the Stack starts it (`install/launcher.py serve --offline ... --max-context 131072 --max-cache-disk 0 --idle-release off --thinking-token-budget 2000`), the Stack's environment (`splashEnv`), a copy-on-write copy of the Stack's Splash home and hub (the live data and the live engines on 127.0.0.1:8770 were not touched), its own ports, under `gate-lock.sh heavy`, one run at a time. Then `backend/scripts/chat-engine-bench.ts` (5 repeats, 128 tokens, short and ~2,500-word prompts, idle and beside a second request), a Messages and a tool-call check, 10 idle minutes (chat), and two `kill -9` of the engine child to time recovery. Studio: 128 GB, load average about 18 from other sessions during all runs, so absolute numbers are noisy; both versions ran back to back under the same load.

Coding, long prompt beside a second request: decode 63.8 against 90.0 tok/s is the one row where 1.6.0 is slower, p90 507 against 191 ms; five repeats under load 18, not repeated.

| Chat engine, 10 idle minutes | 1.4.1 | 1.6.0 |

| Restart after `kill -9` of the engine child | 1.4.1 | 1.6.0 |
|---|---|---|
| chat, first / second | 9.1 s / 13.4 s | 15.9 s / 18.1 s |

Requests returned 503 while the engine was down and 200 after; the second kill inside 60 s was not delayed by the new backoff (5 s step) beyond a few seconds.

## What this does and does not show about past issues

- getmaipai/home 262 (chat slow every ten minutes after an engine restart): not reproduced on either version, so not shown fixed. No restart happened in ten idle minutes on 1.4.1 or 1.6.0 when the Stack was not involved; the cause named in the issue is a Stack-side `recycleRole` call.
- getmaipai/home 263 (coding engine fails to start, Metal compiler error 159 under launchd): not reproduced; this bench ran from a shell, not the Stack's launchd service. Not shown fixed.
- SPLASH-DISK-01 and HOST-GUARD-04: the 1.6.0 ledger and the SSD-cache shrink target them, but a 10-minute idle bench cannot show the multi-day footprint; not shown fixed. The Stack keeps `--max-cache-disk 0`.
